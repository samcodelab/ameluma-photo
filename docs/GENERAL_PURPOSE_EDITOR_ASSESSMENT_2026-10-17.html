Ameluma Photo: general-purpose editor assessment and proposal

Review proposal • 17 October 2026 • implementation not started

Recommendation: evolve the current editor into a document-capable editor, preserving the existing photo engine and workspace. Build a portable, layered document foundation before adding pixel tools. The present application is a capable recipe-based photo utility; it is not yet a general-purpose raster editor.

This review covers the working tree at 62ba1af plus all current tracked and untracked implementation files. The working tree contains substantial earlier work; nothing has been discarded, committed or pushed. This document is the three requested pre-implementation deliverables. It does not approve or implement the proposed architecture.

What the current model can and cannot support

ProcessingConfiguration describes one source photo: geometry, adjustments, one creative filter, enhancement, recolouring, retouch strokes, protective masks, annotations, watermark and export settings. ConfigurationPatch provides sparse, field-specific overrides over batch settings. This is valuable and must remain intact. It does not express arbitrary interleaving of photos, text, paint, groups and effects.

The observed render order is: oriented decode → user rotation/flips/straighten and base adjustments → legacy look → crop and placement/scale → Auto Enhance and creative preset on the framed photo → canvas/shadow/background → recolouring → retouch → privacy masks → annotations/canvas styling → watermark → final opaque-format matte and colour conversion → encode/validate/publish. Preview and export share these definitions. Reordering this pipeline globally would change old saved output.

The current implementation also couples canvas opacity to the selected output format. A transparent document must remain transparent regardless of whether its next export is JPEG. The new compositor therefore needs a format-independent render boundary; only export should flatten unsupported transparency.

Requirements to challenge or simplify

  • Move portable editable saving from P1 to P0. Shipping editable layers before reliable reopening creates user work that cannot safely be preserved.
  • Keep ordinary photo editing lightweight. Opening a workspace photo should retain its current recipe and sparse inheritance; explicit New Document/Open as Layers creates a composition. Both use the same editor shell and canvas, without a tool-driven screen switch.
  • Do not expose every new tool permanently. Group selection tools and shapes; contextual options beside the active tool; show Layers only when needed or explicitly requested. History is an alternate panel, not a permanently stacked inspector.
  • Keep one creative preset per target initially. The older preset contract explicitly replaces rather than stacks. General ordered effects can arrive later in layered documents; do not change saved preset semantics or duplicate the 24 looks under effect names.
  • Basic text and shapes first; full typography later. P0 should provide real editable font-size-based text and fill/stroke shapes. Rich spans, outlines, shadows, distribution and perspective follow only after persistence and transformations are solid.
  • Keep advanced groups and adjustment layers later. Establish a recursive-capable schema and explicit group-compositing semantics now, but ship flat basic layers first. Grouping is not simply hiding several rows: opacity and blend isolation affect pixels.
  • Retouch stays an independent quality gate. Neither layers nor Vision foreground masks solve reconstruction of a missing branch or correct shirt texture. Preserve old stroke recipes and the experimental-removal restriction.
  • Mac first for new layered authoring, shared Core throughout. Build both targets at every milestone. Mobile keeps current photo editing and must render/read new content faithfully before document exchange is offered; never silently flatten or drop unsupported editable content.

2. Proposed Architecture

A. Bounded extension of the current application

Add a shared EditorDocument composition model and a focused document session, not a second application or replacement workspace coordinator. Keep SourceAsset, ProcessingConfiguration, legacy storage paths and workspace schema compatibility. The session owns document revision, active layer IDs, on-canvas selection, viewport, transient manipulation, history and save identity. Existing Workspace remains responsible for imports, gallery membership, batch inputs and creation navigation.

Make the editing target explicit: photo(sourceID) or document(documentID). Within a document, commands name document, layer IDs, region and expected revision. Workspace selection is never read implicitly by an editor command. Resolving Apply/Discard/Cancel for existing drafts remains mandatory before switching targets.

B. Semantic, versioned document and resource model

EditorDocument
  schemaVersion, documentID, revision, displayName
  canvas { integer pixel width/height, profile, transparent/fill }
  ordered LayerNode[]
  embedded resource references and content revisions
  optional metadata / feature requirements

LayerNode
  stable ID, name, visible, locked, opacity, blendMode
  local bounds + affine transform into document coordinates
  content: image | text | shape | drawing | group | adjustment
  optional ordered effects / persistent masks (later)

EditorSession (not serialized as image content)
  current target, active layer IDs, tool, viewport
  active region selection, transient interaction, undo/redo
  savedRevision, recoveryRevision, render generation

Use top-left document pixels as the document coordinate system, doubles for subpixel transforms and local geometry, and one explicit conversion at Core Image/Core Graphics boundaries. Derive display coordinates from one viewport transform. Legacy normalized overlay geometry remains inside the legacy recipe boundary; do not rescale it as though it were new document-pixel text.

Reuse the existing source/resource resolution path. Extend it to resolve resources owned by a portable package, with canonical resource IDs/content hashes and owner references. Workspace visibility is separate from ownership. Do not create a competing global source registry. Identical bytes can be shared within a package; resource identity and photo identity remain distinct.

Layer content should be strongly typed Codable data. An image layer references immutable source bytes plus a captured photo configuration and recipe version. New text and shape payloads retain semantic layout/style records; drawing layers reference sparse raster tiles and/or deterministic stroke records. A new document from a workspace photo captures its effective edits and resources, so later batch changes cannot silently change that document.

Unknown features must be preserved and reported. Support read-only use of a validated stored flattened preview where appropriate, clearly marked; block fresh export/editing if unavailable nodes cannot be rendered faithfully. Never silently export a partial stack. Validate dimensions, finite transforms, unique IDs, resource sizes, tree depth, cycles, node counts and required feature versions.

C. Shared rendering, not another photo engine

Extract narrow internal render stages from ImageProcessor, protected by golden/pixel regression tests. Preserve the public legacy photo-render route and its exact order. A composition renderer orchestrates those existing stages for image-layer content, renders semantic objects using shared primitives, transforms each node, blends into the canvas, then hands the flattened result to the existing encoder and safe publication path.

  1. Resolve immutable document/resource snapshot and requested region/scale.
  2. Render only dirty layer content: original decode/orientation and captured photo recipe, or text/shape/drawing content. A legacy photo node retains the legacy pipeline including protective overlays and watermark.
  3. Apply layer-local region effects/masks when supported; apply local transform with defined sampling.
  4. Composite ordered nodes into the document canvas using explicit premultiplied-alpha blend semantics.
  5. Apply optional document adjustment nodes in a later version with precisely defined scope.
  6. Apply output profile/soft-proof transform. Encoding, metadata policy, matte, validation and collision-safe publication remain the established export responsibility.

For v1 new compositions, choose an explicit SDR sRGB colour contract with half-float intermediate buffers and colour-managed source conversion. Define where perceptual preset recipes enter their existing sRGB working space and where they return; test all eight blend modes against approved reference pixels. Do not guess that arbitrary Core Image defaults match the intended Photoshop/other-app appearance. Wide-gamut preservation, HDR development and arbitrary profile editing require a later designed contract; source bytes stay unchanged.

Preview and export consume the same immutable node graph and recipe versions. Lower-resolution previews may approximate sampling but must preserve geometry, masks, effect scales and grain seeds. Export freezes document revision/resources when queued. Editing afterward cannot affect the queued result. Transparent output remains separate from display checkerboard and JPEG matte.

Privacy behaviour requires particular care: retain existing mask-before-annotation/watermark photo semantics. New layer effects must not expose original masked pixels, and exports must flatten masks and omit disallowed source metadata. New pixel reconstruction/clone paths must not sample supposedly protected regions. Warn that an editable package includes original resources and is not a privacy-sanitized sharing artifact; sharing a finished result uses flattened validated output.

D. Selection is a reusable coverage resource

Introduce one on-canvas RegionSelection per document session, entirely distinct from gallery selection and object/layer selection. Use a bounded sparse alpha coverage mask with a document coordinate transform; allow rectangle/ellipse/path primitives to remain analytic until raster coverage is needed. Add/subtract/intersect/invert must define mask algebra consistently. Feather is a non-destructive parameter on coverage, not repeated blur of the last result.

Mouse/touch input immediately displays a provisional outline and light tint; it never waits for decoding, Vision, flood fill or final rendering. Draw the cursor at display rate independently of render scheduling. A generation token guards asynchronous refinement; retain the previous/provisional usable selection on failure and provide cancel. Reuse and generalize the native pointer adapter already used by retouch/recolour.

Magic wand operates on an explicitly chosen active-layer or merged-visible sample snapshot. Tolerance uses a documented colour-distance metric; contiguous flood fill and non-contiguous matching share that metric, bounded work, cancellation and tile boundaries. Object selection uses the existing local Vision path as a distinct assist with honest failure states; it is not the same algorithm as wand or a guarantee of semantic object separation.

Persistent local effects capture the coverage mask at application time; later selection changes cannot alter earlier edits. Move/copy/transform pixels create a floating-content operation that resolves as one layer/command with undo, never an implicit destructive mutation of the source image.

E. Unified editing operations and history

Use a small typed command set for add/remove/reorder, update transform/style, replace layer effect, and raster tile edits. One interaction transaction spans pointer-down to pointer-up or a slider gesture; transient state is displayed during the gesture, and commit creates one named undo step. Cancel restores the pre-gesture state.

Document history should store semantic deltas and immutable resource references; raster changes store before/after touched-tile versions, not full-resolution image copies. Bound by bytes as well as step count. Keep resources reachable from current document, undo/redo, recovery and queued exports. Prune only after every owner releases them.

Keep the existing workspace history for photo/batch records and the existing creation histories until deliberately integrated. Route macOS Undo/Redo to the active editing target, resolving transient edits first. A document history command must never undo an unrelated photo/batch change. Bridge to native UndoManager labels/menu validation at the platform boundary without maintaining two competing history authorities. Saved content survives reopening; persistent undo is deferred, while crash recovery saves the latest committed document.

F. Portable .ameluma package and safe save lifecycle

Example.ameluma/
  manifest.json             # format version, IDs, canvas, ordered nodes
  Resources/<resource-id>   # immutable images, tile/mask data, custom profile if supported
  Preview.png               # optional flattened display preview

Use a package directory rather than a bespoke binary format or dependency-heavy archive. Saving an editable document embeds/copies its required source resources, unlike current lightweight local workspace instructions. This new behaviour is explicit; do not reinterpret old workspace project files or rename their storage locations. New document save/open, modified indicator, save-as-copy, close/recovery and source retention belong in P0.

Save to a staged sibling package, validate its manifest/resource closure and then atomically publish/replace through a coordinated native document-save adapter. Preserve the previous good version on failure. A plain Data.write(.atomic) on manifest JSON is insufficient for a multi-file package. Handle disk-full, cancellation, permissions, interrupted saves, duplicate resource writes and reopening after workspace cleanup. Reject path traversal, escaping symlinks, malformed/cyclic references and unreasonable allocations on open.

Native macOS file association, file coordination, document change tracking, clipboard and drag promises belong in the Mac adapter. SwiftUI remains the shell; use focused AppKit canvas/input/text bridges where reliable native interaction requires them. No AppKit or UIKit enters FramepebbleCore. No signing or distribution identity changes are needed for this proposal.

G. Performance and canvas ownership

Retain one persistent canvas host per active document/photo and a stable viewport during tool changes. Supply it render surfaces plus lightweight interaction overlays. Refactor the current crop/overlay/recolour internal views incrementally behind this host rather than rewriting all tools at once. One coordinate mapper and input session should own pointer capture, modifier keys, hit testing and selection feedback; options panels should not own image decode.

Cache by resource content revision, captured recipe/effect version, local content revision, transform, requested region, output dimensions/backing scale and colour-space contract. Do not invalidate decoded content when a layer name or selection highlight changes; moving an image should reuse its content render. Use bounded render queues and cancel/coalesce obsolete jobs. Separate export work from current canvas work. Reuse a small set of contexts; fresh mutable filters per job.

Introduce sparse tiled storage/history before paint and eraser ship. Scope layer caching to measured need; avoid building a general GPU graph compiler now. Viewport-tiled rendering can follow the basic layer milestone if whole-surface memory exceeds the defined budget. Current limits of 20,000 px per side/100 MP do not imply a hundred-megapixel multilayer document will fit memory.

H. Workspace, GIF and mobile integration

  • Open photo: current photo recipe and explicit source target; no automatic composition conversion or batch changes.
  • New / Open as Layers: new document with source-sized canvas by default, stable ordered IDs and captured configs. Do not inherit the legacy 1600 × 1200 output canvas.
  • Duplicate as Document: independent editable graph with safely shared immutable resources and independent future edits/history.
  • Export to Workspace: publish a validated flattened revision and import it as a new source. Preserve the editable document separately.
  • Send to GIF: initially render/import an immutable flattened revision and use the current GIF source/config snapshot model. No live document link that changes an existing animation. Preserve masks, resource ownership and review flags.
  • Batch: keep existing explicit captured photo inputs; do not apply arbitrary layer operations in bulk. Later batch effect commands may reuse shared recipe definitions with explicit target snapshots.
  • Mobile: retain single-photo Back navigation; the package/render schema is shared. New authoring surfaces adapt rather than copying the Mac layer inspector onto iPhone.

Performance acceptance proposals

Freeze budgets on a declared baseline before promising them. Suggested targets: visible cursor/lasso feedback on the next display frame with no render dependency; warm 1600-pixel preview adjustments p95 under 80 ms; cancellation acknowledged promptly; stable memory after repeated tool/document switches. Measure pointer-to-visible-feedback and committed-stroke-to-visible-result, not only renderer execution. Record cold decode separately. Add representative 24 MP photos, transparent screenshots and a 10-layer mixed document. Choose a measured memory cap and safe refusal/reduction policy rather than advertising unlimited layers or arbitrary megapixels.

High-risk regressions to keep in the release checklist

  • Old sparse overrides or default sizing changing output; normalized overlay positions changing during conversion.
  • Photo editor commands accidentally using workspace selection; document Undo reaching another photo or batch.
  • Format-dependent matte/alpha, wide-gamut colour shifts, premultiplication halos and blend disagreement.
  • Cleanup deleting package, undo, saved creation or queued-export dependencies.
  • Layer rename/selection triggering a source decode; broad whole-document invalidation on brush movement.
  • Late Vision/render tasks overwriting newer document revisions or restoring content after close.
  • Crash/package save interruption and missing fonts/resources; unsupported newer nodes silently disappearing.
  • GIF frame snapshots becoming live document references; edits altering previously exported files.
