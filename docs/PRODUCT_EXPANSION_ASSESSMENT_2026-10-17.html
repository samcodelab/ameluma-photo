Ameluma Photo product expansion

Repository assessment • architecture proposal • phased roadmap • 17 October 2026

Recommendation: finish the connections between the capabilities already present, then make watermark design and reusable processing the differentiators. Preserve the existing photo engine and new document foundation. Do not continue building a broad Paint.NET-style raster toolbox before the everyday workspace, annotation, batch and creation flows feel like one product.

This proposal follows the latest brief: Ameluma is an everyday image workspace/productivity utility, not a Photoshop competitor or managed photo library. The review covers the current working tree, including earlier uncommitted changes and the new layered-document implementation, not only the last commit 62ba1af. No application, test, project, signing or distribution code was changed for this assessment. Implementation requires approval.

What should change in the earlier plan

  1. Keep the existing layer/document work, but change its purpose and priority. Use it for compositions, screenshot graphics and watermark design. General painting, adjustment layers and Photoshop-style feature coverage no longer drive the roadmap.
  2. Batch processing needs product design, not another engine. The shared fixed pipeline already handles the main operations safely. Make its target, inherited settings, final dimensions, output count and retry behaviour obvious.
  3. Watermark design is a genuine new capability. A text-or-image toggle plus saved values is insufficient. Reuse document/layer primitives for an intentionally constrained graphics designer and reusable, owned designs.
  4. Profiles, recipes and automations must mean different things. Output profiles describe a result variant; recipes describe reusable intent; automations decide when/where to run it. Reusing one stored full-photo configuration for all three will carry unwanted source-specific state.
  5. Do not offer arbitrary recipe reordering before the renderer honours it. Displaying a movable list that compiles back to an unchanged fixed configuration would be misleading. Start with canonical, clearly labelled stages and add only real supported ordering.
  6. Keep the 24 original filters. Add curated tags/entry points, a small named user look library and photographic validation. Seven collection labels do not justify adding seven new sets of recipes.
  7. Do not call blur or pixelation secure redaction. Reserve permanent redaction language for flattened opaque exported coverage after format/container/metadata checks. Editable .ameluma documents include originals and must remain clearly distinct from sanitized outputs.
  8. Ship native background removal later, with real alpha masks. There is a native path and reusable request code, but the current hue-constrained polygon outline is not a cutout-quality matte.

Confirmed integration risks worth addressing first

  • saveProfile removes masks, annotations, retouch and the privacy-export flag but leaves colourReplacements and resolved autoEnhance. This confirms inappropriate generic recipe inputs can be captured. It is not evidence that every export currently applies them incorrectly; profile/source precedence is more nuanced and must be transition-tested.
  • exportConfiguration merges source edits, profile values and sparse overrides deliberately. A recipe must use explicit field ownership; do not silently redefine existing saved profile precedence.
  • WatermarkConfiguration has one content kind. The renderer also has a strict stamp size limit. Adding multi-element designs without bounds/caching could repeat expensive text/logo work hundreds of times or exceed current buffer assumptions.
  • EditorDocumentRenderer invokes the photo processor for image layers. Making the photo watermark renderer invoke the full document renderer in return risks recursive processing. Share small graphics primitives instead.
  • New document creation is functional but mostly exposed in Mac File commands. A user selecting images in the workspace should find Compose beside Batch and Create GIF, with the same captured IDs.
  • Current GIF quality presets chiefly alter dimensions. Renaming them as genuinely different photographic optimisation levels without implementing/measuring that behaviour would be inaccurate.
  • Source cleanup, relinking and review state already protect saved work. New watermark/recipe resources must join that dependency accounting before their UI ships.

2. One action target contract and a coherent editor shell

Use a small explicit target description at command entry: current photo ID, captured workspace image IDs, current document ID, or selected layer IDs within that document. Keep active view, gallery selection, captured operation inputs and on-canvas region selection separate. The request also carries the relevant source/document revision and operation name/count.

Menus, toolbar, context menu and Command-K should call the same established action methods through thin descriptors. Existing startBatchAction, workflow selection contexts, plannedRequests, openPhotosAsDocument and draft-resolution helpers remain the implementations. This is focused routing, not a coordinator rewrite.

Right-clicking an unselected thumbnail uses that image alone; right-clicking a selected image may use the explicitly labelled selected group. Double-click opens one image. A command issued in an image/document editor must not default to all workspace images. “Selected” must distinguish workspace images from document layers. Filtering may hide selected images but never silently changes captured inputs.

Unify header/action placement, toolbox orientation, status, zoom vocabulary and contextual property presentation between the photo and composition surfaces. Preserve a persistent canvas/viewport across tool changes. Import/export/system destination pickers may use native surfaces; changing the active image tool should not open another editing window. Keep one chosen toolbox/options arrangement per layout rather than displaying floating options and a duplicate inspector together.

Share controls against explicit field bindings and target adapters. Photo settings retain sparse inheritance; a document image layer edits its captured configuration. A common inspector must not replace whole per-photo configurations or flatten independent layer settings. Mobile remains buildable and keeps its existing single-image navigation; the new Mac priorities do not authorize a desktop interface on iPhone.

3. Preserve the current render contract; factor only reusable boundaries

The observed photo order is oriented decode → user geometry and base adjustments → legacy look → framing/scale → Auto Enhance and creative filter → canvas/background/style → recolouring → retouch → privacy masks → annotations → watermark → final colour/matte/encoding/validation/publication. Keep legacy recipe versions and saved effective output unchanged.

Extract shared text/shape drawing, graphic element transforms and stamp composition from the current annotation/document/watermark implementations, guarded by pixel fixtures. Keep the photo pipeline public boundary stable. New recipes either compile to this existing order or explicitly execute a supported sequence of CIImage stages. Encoding remains terminal; no compressed-file round trips between steps.

Preview and export use one frozen resolved request, with the same dimensions, crop, watermark design snapshot, mask coverage, colour transform and encoding path. A visual proof that measures bytes is distinct from a fast approximate canvas preview. Do not label a pre-encoding file-size estimate exact.

4. Watermark designer: a constrained reusable graphic document

Recommended design record: stable design ID, name/tags, schema/recipe version, transparent artboard/bounds, ordered editable text/shape/logo elements, owned resource references and optional preview. Reuse typed layer geometry/styles and the existing package resource ownership model. The authoring shell should be the existing canvas with a Design Watermark purpose, not an unrelated app-like window.

Allow installed/system fonts, text+logo combinations, relative element placement, alignment/spacing, colour, opacity, rotation, scale, simple outline/shadow and transparent output. A logo element must be a plain owned graphic with restricted settings: no nested watermark or arbitrary live photo-document reference. The stamp renderer should use shared graphics primitives, never call the full document renderer which itself calls ImageProcessor.

Separate design from application. Design specifies the mark’s internal appearance; application specifies relative output width, anchor/custom position, margin, overall opacity/rotation and repeating pattern. The existing nine-position placement/tiling definition is reused. Changing photos should not move elements inside the design.

Keep an app-wide local saved-design catalog, not another photo library. Use existing portable resource/package helpers with named stable records, thumbnails, duplicate/rename/delete and usage-aware resource retention. Save the design once; when applying it, capture its version/content so later catalog edits do not silently change existing photos, recipes, GIFs or queued exports. Offer explicit Update to Latest where appropriate.

Extend the existing watermark model with a versioned design snapshot while preserving legacy text/image kinds exactly. Resolve its resources through the same ownership/resolution path. Factor a bounded stamp renderer that runs inside the existing processing worker. Cache by design version, resource/font identity, target pixel dimensions and colour contract. Render text/shapes at the requested stamp size rather than permanently baking a small PNG and upscaling it for every export.

Ship about 12 original, visually approved starter designs with overlapping category tags across the ten requested categories: signature line, thin rule, studio stack, copyright line, logo lockup, initials badge, corner monogram, decorative underline, social handle, editorial credit, frame label and repeating mark. These are proposed original art directions, not finished approved assets. Tiling is an application pattern, not another renderer. Test on light/dark/textured photos, portrait/landscape, small images and large batches; avoid decorative-template quantity as the acceptance metric.

A recipe owns only chosen fields. Source-specific traces, masks, annotations, retouch samples, manual framing and resolved enhancement from one image must not enter a generic recipe accidentally. Preserve each image’s grain seed and independent edits unless the recipe explicitly replaces that category. “Convert to PNG” does not introduce a 1600 × 1200 Fit canvas.

Keep existing saved output profiles compatible. Add an explicit Save as Recipe conversion surface that shows included/excluded fields and does not mutate the old profile. Legacy saved profiles and AutomationRecipe values must continue reproducing their old semantics; improvements to new recipe capture are prospective.

First version: canonical labelled stages such as Geometry → Corrections/Look → Watermark → Output. Enable/disable and parameter editing are real. Reordering is available only where execution honours it. If user-controlled order materially changes pixels, persist that order and version and render actual CIImage stages; do not merely rearrange cards. Mandatory protective/output constraints remain explicit. Add arbitrary multi-pass ordering only after crop/resize coordinates, previews, and field inheritance pass tests.

Watched-folder automations remain a Mac adapter that chooses when and where to run a frozen recipe. Keep stability checks, overlap protection, review-before-publication and retry ledgers. Do not replace useful Automations with a second recipe engine.

6. Annotations, numbered callouts and redaction

Extend the existing editable annotation records/renderers. Add highlight as a defined fill/opacity style and numbered callout as a semantic type with a stable marker ID/sequence. Derive displayed numbers from callout order, with start/group settings only if needed. Deleting/reordering markers renumbers them; Undo restores numbering. Do not store numbers only as raster text or use unstable visible-grid indices.

Reuse text/shape primitives between photo annotations, composition layers, GIF annotations and watermark elements; keep coordinate adapters explicit. Legacy normalized output geometry and width-scaled text must render as before. New explicit font-size/style fields need versioned defaults rather than silently restyling old captions.

Redact should mean an opaque flattened cover in the exported pixels. Blur/pixelation remain separate visual effects. Verify selected coverage after crop/rotation, multiple masks, alpha, JPEG boundaries and every exported GIF frame. Validate that finished files contain no copied source thumbnails/attachments/layers or disallowed metadata. Packages, undo and local originals retain sensitive content by design; never claim secure deletion of local sources, caches or projects. Show Save Editable versus Export Finished clearly.

7. Connect existing creations before adding more layouts

Expose Compose Selected beside Batch and Create GIF. Curate the existing collage patterns into six everyday starting tasks: side by side, before/after, image grid, captioned image, screenshot sequence and feature image. Preserve the complete existing catalog behind More Layouts. Layout helpers may create initial EditorDocument layer placements where practical; they must not become a third layout engine or rewrite saved collages.

Default before/after exports should compare visual edits while retaining protective overlays and matching geometry. Do not silently add an unredacted original panel to an otherwise redacted image. A user explicitly choosing unedited source content needs a clear preview/review of that choice.

Bridge documents to GIF/workspace through a validated immutable flattened revision at first, reusing managed source acquisition and retained ownership. No user-managed export/reimport dance, no duplicate source registry, and no live link that changes an already-created GIF when a document is edited later.

GIFs already retain photo watermark settings in captured frames. Add an explicit animation-wide watermark snapshot after the finished frame is fitted/annotated if needed; distinguish it from marks already attached to source photos. Preserve source settings and never silently remove them to avoid a double mark. Keep frame identities, timing and annotation visibility across every bridge. More GIF presets should first be honestly named use-case dimension/timing suggestions; real palette/dither optimisation needs measured visual/size evidence.

8. Filters and export remain shared

Retain existing stable preset IDs and recipe versions. Natural/Portrait/Cinematic/Vintage/Black & White/Creative/Film can be user-facing tags or curated views of the 24 looks; do not invent a portrait-specific benefit without skin-tone review. A named custom look should save only the selected recipe version/intensity (and deliberately chosen safe look parameters), not a full photo edit. Auto Enhance remains an independent per-photo correction.

Use current encoder/target-byte proof and capability checks across photo, batch, composition and recipe export. Add the missing document export sizing/proof/profile bridge through the same planner/encoder. Preserve profile/metadata policy where supported; new layered composition rendering is currently SDR sRGB, not HDR/wide-gamut-preserving editing. WebP is offered only when the native writer exists; unsupported output never silently falls back to another format.

9. Command-K without a separate processing path

Start with deterministic action search, synonyms and small typed parameter parsers. Entries route existing methods. No remote language service or image upload is needed. Show a prospective action such as “Resize longest edge to 1920 px · 12 selected images (3 hidden)” or “Export current document · 1 image”. Make width versus longest-edge defaults visible.

Resolve target IDs when the user commits the command, then freeze them. Reject stale/missing targets with a useful recovery path. A changed tool draft uses the existing Apply/Discard/Cancel contract. The palette must not advertise background removal or other unavailable actions as functional. Simple routing can ship early; parameterised recipe commands follow the shared planner.

10. Native background removal: feasible, not yet a completed feature

Apple supplies foreground instance masks and image-scaled masks that can support local subject cutouts. Apple Vision request documentation and scaled-mask documentation support investigating this route. Hardware/runtime capability and image quality still need testing.

Keep a source-oriented alpha matte, analysis version and source-content identity; apply it before the source’s existing framing/overlays, with explicit background fill/replacement. Reuse the native request groundwork but not the recolour hue mask or polygon simplification. Default to keeping detected foreground subjects with a way to select the intended instances. Analyse off the main thread, show immediate request feedback, support cancellation, and preserve the previous image on failure. Relinking invalidates the matte/review state.

Initial transparent output needs a supported alpha format; make that decision explicit. Fine hair, glass, shadows, similar foreground/background and small subjects are quality gates, not guaranteed results. Manual correction follows a suitable persistent mask/drawing foundation; do not promise a professional refine-edge tool from a basic binary outline.

11. Persistence, ownership and history

Keep workspace instructions (schema 4, local references), portable image documents (version 1), named designs and recipes conceptually distinct but under shared validation/resource helpers. New semantics that an older reader would silently drop need explicit feature/version negotiation or a schema bump with tested migration. Never change saved output by adding a decoding default to an existing recipe.

Photo edits keep sparse patches and workspace timeline compatibility. Documents/designs use semantic command deltas or bounded semantic states; future raster edits need touched-tile history rather than full-resolution bitmap copies. A slider/drag is one undo transaction. Resolve the active target before routing Undo; a recipe apply groups only successful commits and cannot undo a newer unrelated edit.

Expand dependency enumeration before new saved resources ship: current/saved documents, designs, recipes, GIF/collage snapshots, pending exports and session Undo/Redo. Workspace removal affects visible membership; deleting a design differs from freeing an unreferenced local copy. Missing or unreadable dependency records make cleanup fail closed. Keep staged atomic persistence, immutable resources and original preservation.

12. Performance and interaction quality

Reuse dedicated interactive workers, bounded preview/content caches and source fingerprints. Prioritise current canvas over visible thumbnails; coalesce sliders, reject obsolete generations and release inactive buffers. Moving a layer or changing selection should not decode an unchanged source. Cache rendered watermark stamps per actual size/version and reuse them across batch jobs.

Retain conservative batch concurrency until real profiling justifies increasing it. Measure 100/500-image runs with bounded memory, cancellation and retry; do not preload full-resolution collections. Measure pointer-to-feedback and input-to-visible-result on declared hardware, separately from cold decode, warm render or isolated kernels. Existing engine timings and hosted captures cannot establish exceptional macOS performance.
